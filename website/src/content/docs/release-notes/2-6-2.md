**Released:** 2026-11-19

Kure Monitor 2.6.2 is a performance and stability patch release focused on large multi-node Kubernetes clusters. It eliminates `/api/pods/failed` query timeouts (`500` errors) on clusters with large `pod_failures` tables, stops N× duplicate reporting across DaemonSet agent pods, and automatically prunes old `resolved` rows so the database stays lean.

### Headline Changes

- **Sub-Millisecond `/api/pods/failed` Queries on Large Clusters**: Pushed active status filtering (`status IN ('new', 'investigating')`) inside the `DISTINCT ON (pod_name, namespace)` query and added composite and partial PostgreSQL indexes so dashboard loads only scan active failing pods rather than hundreds of thousands of historical resolved rows.
- **Node-Scoped DaemonSet Agent & Backend Deduplication**: Each `kure-agent` DaemonSet pod now receives its `NODE_NAME` via the Kubernetes Downward API (`spec.nodeName`) and only reports pods scheduled on its own node (plus unscheduled `Pending` pods). Added a PostgreSQL advisory lock in `save_pod_failure()` to eliminate race-condition duplicate inserts.
- **Automatic Cleanup of Resolved Pod Failures**: Added a background cleanup loop in the backend that prunes `resolved` `pod_failures` rows older than 24 hours on startup and every hour, preventing unbounded table growth.
- **Better Exception Diagnostics**: Updated `/api/pods/failed` error logging to include `{type(e).__name__}` and tracebacks so `asyncio.TimeoutError` exceptions are clearly visible in logs.

---

## Upgrade Notes

If you are upgrading an existing large cluster where `pod_failures` has already grown large, the new startup cleanup will automatically prune `resolved` rows older than 24 hours. To immediately reclaim disk space in PostgreSQL after upgrading, you can optionally run:

```sql
VACUUM (ANALYZE) pod_failures;
```
